## 一、项目描述(简历 / 自我介绍直接用)

### 1.1 一句话概括

> 基于 Spring Boot 3 + MyBatis-Plus + MySQL + Redis + Vue 3 的前后端分离**后台管理系统**,实现 JWT 登录鉴权、
> 用户/角色管理,登录态存 Redis 支持主动注销与强制下线。

### 1.4 可以主动说的三个亮点

1. **JWT 不是"无状态死结"**:额外用 Redis 存登录态,既保留 JWT 免查库的优势,又实现**注销/强制下线/续期**——这是对"JWT 无法注销"这一经典缺陷的工程解法。
2. **工程化细节**:统一响应体 + 全局异常 + 参数校验 + 密码序列化保护(`@JsonIgnore`)+ 内置数据初始化(幂等种子数据),接口层不用重复写样板代码。
3. **环境可复制**:一键启停脚本(幂等端口探测、缺依赖自动构建/安装、日志归集),把"新机器跑起来"从半小时压缩到双击一次。

### 2.2 一次请求的完整链路(面试画图/口述)

**登录请求**
```
浏览器 → Vite devServer(:5173) 代理 /api → Spring Boot(:8080)
  → AuthController#login
  → AuthService: 按 username 查 sys_user → BCrypt.matches 校验 → 账号状态校验
  → JwtUtil.createToken(userId, username)                 // HS256 签名
  → StringRedisTemplate.set("aki:login:token:{token}", userId, TTL 8h)
  → 返回 { code:200, data:{ token, user{...} } }
前端:token 存 localStorage,Pinia 保存用户信息,跳转首页
```

**业务请求(如用户列表)**
```
axios 请求拦截器:Authorization: Bearer {token}
  → AuthInterceptor#preHandle:
       ① 解析 JWT(jjwt 校验签名与过期)  ② 查 Redis 是否存在该 token
       ③ UserContext.set(userId, username)     // ThreadLocal
  → SysUserController#page → SysUserService → MyBatis-Plus 分页插件改写 SQL → MySQL
  → afterCompletion: UserContext.clear()          // 防止线程池复用串数据
```

**登出**
```
POST /api/auth/logout → AuthService.logout(): redisTemplate.delete("aki:login:token:{token}")
→ 该 token 立即失效(即使 JWT 本身还没过期)
```

## 三、项目深挖题(面试官最爱问,答案就是你的代码)

### Q1:为什么用 JWT?又为什么还要存 Redis?这不是自相矛盾吗?

**答**:JWT 解决的是"服务端不用存 session、横向扩展无需共享会话";但纯 JWT 有三个硬伤:
① **无法主动注销**(签发后到过期前一直有效);
② **无法强制下线/改密码立即失效**;
③ **无法控制单点登录**。

我的做法是"JWT 做身份凭证 + Redis 做登录态开关":
- 请求进来先验 JWT 签名与过期(不查库,快);
- 再查 Redis 里是否有 `aki:login:token:{token}`,没有就 401。

好处:登出/强制下线只需删 Redis key;同时保留了 JWT 无状态解析的优点。
代价:每次请求多一次 Redis 查询——本地内存级开销(亚毫秒),换来可撤销性,值得。

**追问:那和纯 Session 有什么区别?**
本质上是"带 TTL 的、可水平扩展的 Session":Redis 集中存储,任意节点都能校验;JWT 里携带用户标识,省掉一次"从 sessionId 查用户"的动作。

---

### Q2:token 过期了怎么办?如何实现续期 / 无感刷新?

**答**:当前实现是固定 8 小时(`aki.jwt.expire-seconds=28800`),过期后前端收到 401 → 清理本地 token → 跳登录页(`api/request.js` 里统一处理)。

**如果要升级为无感刷新**,我会这样做(可作为扩展回答):
- 登录时同时签发 `accessToken`(短,如 30 分钟)+ `refreshToken`(长,如 7 天);
- refreshToken 只存 Redis,并在每次使用时**轮换**(旧的作废),防止被重放;
- accessToken 过期时前端用 refreshToken 调 `/auth/refresh` 换新 token;
- 也可以做"滑动过期":每次请求在 Redis 里对 key 续期(`EXPIRE`),但要注意别无限续导致会话永不过期。

---

### Q3:密码是怎么存的?为什么不用 MD5 加盐?

**答**:用 **BCrypt**(`PasswordConfig` 注册 `BCryptPasswordEncoder`),数据库里存形如 `$2a$10$...` 的哈希。
- MD5/SHA 是**快速哈希**,GPU 每秒能算几十亿次,加盐只能防彩虹表,防不住暴力破解;
- BCrypt 是**慢哈希**,内置随机盐(cost=10 表示 2^10 次迭代),每次加密结果都不同,校验用 `matches(raw, encoded)`;
- BCrypt 的盐和 cost 都编码在哈希串里,不需要额外字段存盐。

**追问:为什么没有引 spring-boot-starter-security?**
这个项目鉴权是自己写的拦截器 + JWT,不需要 Security 的过滤器链和权限表达式,所以只引了 `spring-security-crypto`(拿 BCrypt),减少配置复杂度。如果要做细粒度权限(菜单/按钮级),我会换成完整的 Spring Security + `@PreAuthorize`。

---

### Q4:为什么用 HandlerInterceptor 而不是 Filter 或 AOP?

| 方案 | 特点 | 适用 |
|---|---|---|
| Filter | Servlet 规范层,拿不到 Controller 方法信息,Spring 的 Bean 注入不便 | 编码、请求日志、XSS 包装 |
| **Interceptor** | Spring MVC 层,能拿 `HandlerMethod`、能注入 Bean、能读 `@RequestMapping` 信息 | **登录校验、权限校验(本项目)** |
| AOP | 方法级切面,粒度最细 | 操作日志、事务、限流注解 |

本项目在 `WebConfig#addInterceptors` 里注册 `AuthInterceptor` 拦截 `/api/**`,并排除 `/api/auth/login`。
拦截器里对 `OPTIONS` 预检请求直接放行(否则跨域预检会被 401 拦掉)。

**追问:拦截器里怎么返回统一格式的 401?**
`response.setStatus(401)` + `ObjectMapper` 写回 `Result.error(401, "登录已失效,请重新登录")`,并 `return false` 中断后续处理。

### Q5:UserContext 用 ThreadLocal 存当前用户,有什么坑?

**答**:三个坑,我都处理了:
1. **线程池复用导致数据串用** → 必须在请求结束时清理:我在 `afterCompletion` 里调用 `UserContext.clear()`(`remove()` 而不是 `set(null)`);
2. **内存泄漏** → ThreadLocal 的 key 是弱引用、value 是强引用,不 remove 会一直挂在池化线程上;
3. **异步/子线程取不到** → 如果业务里开了线程池,ThreadLocal 不会自动传递,需要 `InheritableThreadLocal` 或手动透传(`TaskDecorator` / 阿里的 TTL)。

### Q6:统一返回和全局异常是怎么设计的?

**答**:
- `Result<T>{ code, msg, data }`,静态方法 `ok()/ok(data)/error(msg)/error(code,msg)`,前端只需判断 `code === 200`;
- `GlobalExceptionHandler`(`@RestControllerAdvice`)统一处理三类异常:
  - `BusinessException` → 业务提示(如"用户名已存在");
  - `MethodArgumentNotValidException` → 取出第一条字段校验消息(配合 DTO 上的 `@NotBlank/@Size/@NotNull`);
  - `Exception` → 兜底,打日志返回"系统异常"。

**追问:为什么不直接把异常堆栈返回给前端?** 会泄露实现细节(表名、SQL、路径),是常见安全风险。

---

### Q7:MyBatis-Plus 分页插件的原理?你踩过什么坑?

**答**:`MybatisPlusInterceptor` + `PaginationInnerInterceptor(DbType.MYSQL)` 注册为 MyBatis 插件,
执行时拦截 `Executor#query`,**自动改写 SQL 拼接 `LIMIT ?,?`,并自动执行一条 `COUNT` 查询**填 `total`。

**我实际踩的坑(很加分的一个细节)**:MyBatis-Plus **3.5.9 起把分页插件依赖的 JSqlParser 拆成了独立模块**,
只引 `mybatis-plus-spring-boot3-starter` 会报 `找不到 PaginationInnerInterceptor`,
必须额外引 `mybatis-plus-jsqlparser`。这就是"照抄旧教程会翻车"的典型例子,说明我看的是当前版本的官方文档。

**追问:深分页怎么优化?** `LIMIT 1000000,10` 会扫描大量行 → 用**延迟关联**(先用覆盖索引拿主键再 JOIN 回表)或**游标分页**(`WHERE id > lastId ORDER BY id LIMIT 10`)。

### Q8:实体里的 password 字段怎么保证不返回给前端?

**答**:在 `SysUser.password` 上标 `@JsonIgnore`,序列化时直接忽略。
比"每次手动 copy 到 VO"更省事,也不怕漏写;需要返回时用专门 DTO/VO。
另外登录接口返回的是手工组装的 `Map`(只放 id/username/nickname/roleId/roleName),双重保险。

---

### Q9:删除操作做了哪些保护?为什么表里没建外键?

**答**:
- 用户:禁止删除**当前登录账号**(`id.equals(UserContext.getUserId())` 直接抛业务异常),避免管理员把自己删了;
- 角色:① 内置 `ADMIN` 角色不允许删;② 有用户引用该角色时报错并给出引用数量;
- **不建物理外键**:互联网业务常用"逻辑外键 + 索引",原因是外键在高并发写入时容易造成锁竞争、影响数据归档与分库分表;一致性交给应用层 + 事务保证。本项目在 `role_id` 上建了普通索引。

**追问:那怎么保证不会出现"野角色 id"?** 新增/编辑用户时校验角色存在;更强的做法是把角色选择限制为下拉框(前端 `/roles/all`)+ 后端校验。

### Q10:用户名唯一怎么保证?并发下会不会重复?

**答**:两层:
1. 数据库 `uk_username` **唯一索引**(最终防线);
2. 应用层先 `selectCount` 校验并给出友好提示。

**并发场景的诚实回答**:`selectCount` 再 insert 之间存在竞态(两个请求同时通过校验),
唯一索引会拦住其中一个(抛 `DuplicateKeyException`),但用户看到的是 500 而不是友好提示。
**改进**:捕获 `DuplicateKeyException` 转成"用户名已存在"业务异常——这是"检查 + 兜底"的标准组合。

---

### Q11:为什么 Service 里基本没加 @Transactional?什么时候必须加?

**答**:当前每个接口都是单条 SQL 操作(单表 insert/update/delete),MySQL 单语句本身就有原子性,加事务只是多一轮 `BEGIN/COMMIT`,没必要。
**必须加的场景**:跨多表的写操作,例如"新增用户同时写用户-角色关联表"或"删除角色同时清理关联",这时要在 Service 方法上加 `@Transactional(rollbackFor = Exception.class)`。

**追问:@Transactional 失效场景**(高频):
① 方法不是 public;② 同类内部方法自调用(没走代理);③ 异常被 catch 吞掉;④ 抛的是受检异常但没配 `rollbackFor`;⑤ 多线程里操作(事务不跨线程);⑥ 数据库引擎不支持事务(MyISAM)。

---

### Q12:前端是怎么配合鉴权的?

**答**:
1. **axios 请求拦截器**统一加 `Authorization: Bearer {token}`;
2. **响应拦截器**:业务码非 200 弹 `ElMessage` 并 reject;HTTP 401 时清 localStorage、跳 `/login`;
3. **路由守卫**(`router/index.js`):无 token 且目标不是 `/login` → 重定向登录;已登录访问 `/login` → 回首页;
4. 用户信息存 Pinia + localStorage(刷新页面不丢),退出登录调后端接口删 Redis key 再清本地。

**追问:localStorage 存 token 有什么风险?** XSS 可读 → 更安全的是 `HttpOnly Cookie + CSRF Token`,或者短期 accessToken 放内存 + refreshToken 放 HttpOnly Cookie。

### Q13:开发环境跨域是怎么解决的?

**答**:两层:
1. **Vite devServer 代理**(`vite.config.js`):`/api` → `http://localhost:8080`,浏览器视角是同源请求,开发期最简单;
2. 后端也配了 **CORS**(`WebConfig#addCorsMappings`,允许所有来源与方法),方便直接用 Postman/Swagger 或前端直连。
**生产环境**一般用 Nginx 同域反代,前后端都不需要开跨域。

### Q14:一键启动脚本做了什么?遇到过什么问题?

**答**:`start-all.bat`(ASCII 启动器)→ `scripts/start-all.ps1`:
① 检查/启动 MySQL80 服务;② 端口 6379 未监听则拉起 Redis;③ jar 不存在则自动 `mvn package`;
④ `node_modules` 不存在则自动 `npm install`;⑤ 启动后端/前端并重定向日志到 `logs/`;
⑥ 轮询端口直到就绪,打印状态汇总表,自动打开浏览器。全部**幂等**,重复执行只会"[跳过]"。

**踩过的两个坑(真实经历,面试可讲)**:
1. **cmd 代码页乱码**:批处理按系统 ANSI 代码页解析,UTF-8 中文会让解析器错位"吃掉"后面的 ASCII 字符(表现为 `netstat` 变成 `stat`、脚本乱执行)。最终把 `.bat` 降级为纯 ASCII 启动器,逻辑与中文提示放进 **UTF-8 带 BOM** 的 `.ps1`。
2. **配置文件被写入 BOM 导致 Redis 启动失败**:用 .NET `WriteAllText` 默认带 BOM,Redis 解析配置首行报 `unknown conf file parameter`。改用 `UTF8Encoding($false)` 写无 BOM 文件解决。

## 四、Java 基础与集合(必背)

### 4.1 HashMap
- **结构**:数组 + 链表 + 红黑树(JDK8)。链表长度 ≥8 且数组长度 ≥64 时转红黑树,退化到 6 转回链表;
- **扩容**:默认容量 16、负载因子 0.75,元素数超过阈值翻倍扩容,JDK8 用**高低位链表拆分**(不需要重新算 hash);
- **hash 扰动**:`h = key.hashCode() ^ (h >>> 16)`,让高位参与运算,减少冲突;
- **为什么容量是 2 的幂**:`(n-1) & hash` 等价于取模但更快,且扩容后元素位置只可能是"原位置"或"原位置+旧容量";
- **线程不安全**:并发 put 可能丢数据/JDK7 头插成环;安全场景用 `ConcurrentHashMap`。

### 4.2 ConcurrentHashMap
- JDK7:分段锁 `Segment`;JDK8:**CAS + synchronized 锁单个桶头节点**,并发度更高;
- `size()` 用 `baseCount + CounterCell[]` 分散计数;扩容支持多线程协助迁移(`ForwardingNode` 标示)。

### 4.3 线程池(必问)
- 核心参数:`corePoolSize`、`maxPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler`;
- **执行流程**:核心线程 → 队列 → 非核心线程 → 拒绝策略;
- 拒绝策略:AbortPolicy(默认抛异常)、CallerRunsPolicy(调用方执行,天然背压)、DiscardPolicy、DiscardOldestPolicy;
- **为什么不建议用 Executors**:`newFixedThreadPool`/`newSingleThreadExecutor` 用无界队列会 OOM;`newCachedThreadPool` 最大线程是 Integer.MAX_VALUE 会疯狂建线程。**手写 ThreadPoolExecutor**;
- 线程数估算:CPU 密集 ≈ 核数+1;IO 密集 ≈ 核数 × (1 + 等待时间/计算时间)。

### 4.4 并发基础
- `volatile`:可见性 + 禁止指令重排(内存屏障),**不保证原子性**;
- `synchronized`:锁升级(无锁 → 偏向锁 → 轻量级 CAS → 重量级),JDK15 后偏向锁默认关闭;
- `CAS`:比较并交换,ABA 问题用版本号/`AtomicStampedReference`;
- `AQS`:`state` + CLH 双向队列,ReentrantLock/CountDownLatch/Semaphore 都基于它;公平锁与非公平锁的区别(是否排队);
- JMM:`happens-before` 规则(程序顺序、监视器锁、volatile、线程启动/终止、传递性)。

### 4.5 JVM(常问)
- 内存区域:堆、方法区(元空间)、虚拟机栈、本地方法栈、程序计数器;
- 对象创建与分配:TALB、逃逸分析、栈上分配;
- GC:新生代 Eden/S0/S1(复制算法)、老年代(标记-清除/整理);G1 按 Region 划分、可预测停顿;
- 判断存活:可达性分析(GC Roots);
- 常见排查:`jps`、`jstack`(死锁/线程)、`jmap`、`jstat`,OOM 加 `-XX:+HeapDumpOnOutOfMemoryError`。

## 五、Spring / Spring Boot

### 5.1 IoC / DI
- IoC:对象创建与依赖管理交给容器;DI 是它的实现手段(构造器/Setter/字段注入,**推荐构造器**,便于测试且能发现循环依赖);
- Bean 生命周期:实例化 → 属性填充 → `Aware` 回调 → `BeanPostProcessor#before` → `@PostConstruct`/`InitializingBean` → `BeanPostProcessor#after`(AOP 代理在此生成)→ 使用 → `@PreDestroy`;
- **三级缓存解决循环依赖**:一级放成品 Bean,二级放半成品,三级放工厂(为了在需要时提前生成 AOP 代理)。**只支持单例 + Setter/字段注入**,构造器注入的循环依赖无法解决;
- `@Autowired` 与 `@Resource` 区别:前者按类型(Spring 提供),后者按名称(JSR-250)。

### 5.2 AOP
- 原理:动态代理。目标类有接口 → JDK 动态代理;无接口 → CGLIB(继承,`final` 类/方法不能增强);
- 场景:声明式事务、日志、权限、限流、缓存;
- 同源内部调用导致 AOP 失效(没走代理),解决:`AopContext.currentProxy()` 或注入自身/拆类。

### 5.3 事务
- ACID;传播行为常用 `REQUIRED`(默认,有则加入)、`REQUIRES_NEW`(新事务,独立提交回滚)、`NESTED`(保存点);
- 隔离级别:`READ_UNCOMMITTED` / `READ_COMMITTED` / `REPEATABLE_READ`(MySQL 默认) / `SERIALIZABLE`;
- 失效场景见 Q11。

### 5.4 Spring Boot 自动配置
- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`;
- `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector)` 读取
  `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`(2.7+ 新机制,旧版是 `spring.factories`);
- 每个自动配置类上有条件注解:`@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 决定是否生效;
- **自定义 starter**:写 auto-configuration 类 + `imports` 文件 + `@ConfigurationProperties`;
- 启动流程:构造 `SpringApplication` → 准备环境 → 创建 `ApplicationContext` → `refresh()`(扫描、实例化、自动配置)→ 调用 `ApplicationRunner`/`CommandLineRunner`(本项目的 `DataInitializer` 就在这里跑)→ 启动内嵌 Tomcat。

### 5.5 过滤器 / 拦截器 / 监听器
见 Q4 对比表。补充:过滤器在 Servlet 容器层,拦截器在 DispatcherServlet 内,`@ControllerAdvice` 处理异常属于更外层的统一处理。

## 六、MySQL(结合项目表设计来讲)

### 6.1 索引
- **InnoDB 用 B+ 树**:非叶子节点只存索引键、叶子节点存数据且用双向链表串联 → 树更矮(3~4 层可存千万级)、范围查询友好;
- **聚簇索引 vs 二级索引**:主键索引叶子存整行;二级索引叶子存主键值,查其它列要**回表**;
- **覆盖索引**:查询列都在索引里,免回表(本项目分页查 `id, username, nickname...` 若在 `username` 上建索引,按用户名搜索可走覆盖/二级索引);
- **最左前缀**:联合索引 `(a,b,c)` 只能从 a 开始连续匹配;`a=1 AND c=3` 只用得上 a;
- 索引失效:对列做函数/运算、隐式类型转换(`varchar` 列传数字)、`LIKE '%xx'` 前置通配、`OR` 连接非索引列、`!=`/`NOT IN` 视情况;
- **区分度**:性别这种低基数列建索引意义不大。

### 6.2 事务与锁
- **MVCC**:undolog + 版本链 + ReadView,实现"读不加锁";RC 每次查询生成 ReadView,RR 首次查询生成(因此可重复读);
- **锁**:表锁/行锁(基于索引!没走索引会退化成锁全表)、间隙锁(Gap Lock,RR 下防幻读)、意向锁、Next-Key Lock;
- 死锁:两个事务反向加锁;排查 `SHOW ENGINE INNODB STATUS`;避免方式:统一加锁顺序、缩短事务、`SELECT ... FOR UPDATE` 谨慎使用。

### 6.3 优化与排查
- `EXPLAIN` 重点看:`type`(至少 range,最优 ref/const,最怕 ALL)、`key`(实际用到的索引)、`rows`(预估扫描行数)、`Extra`(Using filesort / Using temporary 需警惕);
- 慢查询:`slow_query_log` + `long_query_time`,`mysqldumpslow`/pt-query-digest 分析;
- 常用手段:加合适索引、避免 `SELECT *`、批量插入、读写分离、热点数据进 Redis、大表归档/分表。

### 6.4 结合项目的可聊点
- 表设计:主键 `BIGINT AUTO_INCREMENT`,业务唯一键用唯一索引(`uk_username`、`uk_role_code`),时间字段用 `DATETIME DEFAULT CURRENT_TIMESTAMP` 并在更新列上 `ON UPDATE CURRENT_TIMESTAMP`;
- 字符集统一 `utf8mb4`(支持 emoji),排序规则 `utf8mb4_unicode_ci`;
- 分页 SQL(MP 生成):`SELECT ... FROM sys_user WHERE ... ORDER BY id DESC LIMIT ?,?` + `SELECT COUNT(*) FROM sys_user WHERE ...`;
- 如果数据量大:先 `WHERE id > ?` 游标分页,或延迟关联优化深分页。

## 七、Redis(项目里就在用,讲起来最有底气)

### 7.1 数据结构与底层
| 类型 | 底层 | 典型场景 |
|---|---|---|
| String | SDS(记录长度,二进制安全) | 缓存、计数器、分布式锁 |
| Hash | listpack / hashtable | 对象属性(如购物车) |
| List | quicklist(双向链表+listpack) | 消息队列、最新列表 |
| Set | intset / hashtable | 去重、标签 |
| ZSet | listpack / 跳表 + 字典 | 排行榜、延迟队列 |
- 跳表:多层索引实现 O(logN) 范围查询,比平衡树实现更简单、范围遍历更高效。

### 7.2 缓存三大问题(必问)
- **穿透**:查不存在的数据,每次都打到 DB → 缓存空值(短 TTL)、布隆过滤器、参数校验;
- **击穿**:热点 key 过期瞬间大量并发 → 互斥锁重建(只让一个线程回源)、逻辑过期(不设 TTL,异步续期);
- **雪崩**:大量 key 同时过期 / Redis 宕机 → TTL 加随机抖动、多级缓存、集群高可用、限流降级。

### 7.3 持久化
- **RDB**:定时快照,文件小、恢复快,但可能丢最后一次快照后的数据;
- **AOF**:追加写命令,`appendfsync` 策略(always/everysec/no),丢数据少但文件大、恢复慢;
- **混合持久化**(4.0+):AOF 重写时前半部分用 RDB 格式,兼顾速度与安全。
- 本项目用的 Windows 版 Redis 默认 RDB(`dump.rdb`),并且我把持久化目录显式配置为 `dir C:/tools/redis`,避免它把快照写到项目目录。

### 7.4 过期与淘汰
- 过期删除:**惰性删除**(访问时判断)+ **定期删除**(随机抽样);
- 内存淘汰(8 种):`noeviction`、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-ttl`、`random` 等,缓存场景常用 `allkeys-lru`。

### 7.5 分布式锁
- 基础版:`SET key value NX PX 30000`,value 用唯一标识(如 UUID),释放时用 Lua 校验"是我的锁才删";
- 必须设过期时间(防死锁),但要防止"业务没执行完锁就过期"→ **看门狗自动续期**(Redisson);
- 进阶:Redlock(多节点多数派)、或直接用 Redisson 的 `RLock`(可重入 + 看门狗);
- 更严谨的一致性场景可用 ZooKeeper/etcd(临时顺序节点)。

### 7.6 高可用与扩展
主从复制(全量 RDB + 增量 repl_backlog)→ 哨兵(自动故障转移)→ Cluster(16384 槽分片)。缓存一致性常用**旁路缓存**(Cache Aside):写 DB 后**删除**缓存(而不是更新),并给缓存设 TTL 兜底;强一致要求高时可用 Canal 订阅 binlog 异步删除。

### 7.7 项目实践(直接说这个)
- **为什么把登录态放 Redis**:① 可主动注销/强制下线;② TTL 天然带自动过期,不用自己写清理任务;③ 集中存储,后端多实例横向扩展时行为一致;
- key 设计:`aki:login:token:{token}` → userId,带业务前缀便于排查与批量清理;
- 生命周期实测:登录后 `TTL` 为 28800 秒,登出后 key 立即消失(可用 Tiny RDM 图形化观察,或用 `redis-cli keys 'aki:login:token:*'` 验证);
- **可扩展话题**:若要做"同一账号只能一处登录",可再存 `aki:login:user:{userId}` → token,新登录时删掉旧 token;
  若要做接口限流,可用 `INCR + EXPIRE` 做固定窗口,或用 ZSet 做滑动窗口。

## 十、手写题 / 算法题(高频,建议能手写)

### 10.1 双重检查单例
```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                       // 第一次检查,避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {               // 第二次检查,防重复创建
                    instance = new Singleton();       // volatile 防止指令重排(半初始化对象)
                }
            }
        }
        return instance;
    }
}
```

### 10.2 手写 LRU(LinkedHashMap 版)
```java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);   // accessOrder=true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```
> 追问:线程安全版用 `synchronized` 包一层,或自己写"哈希表 + 双向链表 + 哨兵节点";Redis 的近似 LRU 是随机采样淘汰。

### 10.3 生产者-消费者(阻塞队列版)
```java
BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);
// 生产者
queue.put(task);        // 满则阻塞
// 消费者
Task t = queue.take();  // 空则阻塞
```
手写版要点:`synchronized` + `wait/notifyAll`(用 `while` 而不是 `if` 判断条件,防虚假唤醒)。

### 10.4 算法常见题
- 链表:反转、判环(快慢指针)、合并两个有序链表、K 个一组反转;
- 数组/字符串:两数之和、三数之和、最长无重复子串(滑动窗口)、最大子数组和(DP);
- 树:层序遍历、最大深度、判断平衡、最近公共祖先;
- 排序:快排(手写 partition)、归并(稳定)、堆排;复杂度与稳定性要能背;

## 十一、场景设计题(开放题,分点作答)

### 11.1 接口幂等怎么做?
- 唯一索引兜底(最可靠);
- 前端提交按钮置灰 + 后端 token 机制(先取一次性 token,提交时删除);
- 业务唯一号(订单号)去重表;
- 分布式锁(同 key 同时只处理一次)。

### 11.2 验证码登录 / 短信限流?
- `SETEX sms:code:{phone} 300 code` 存验证码,5 分钟有效;
- 发送前 `INCR sms:limit:{phone}:{yyyyMMddHH}` + `EXPIRE`,超过阈值拒绝(固定窗口限流)。

### 11.3 秒杀系统要点?
- 前端限流/按钮防抖 → 网关限流(令牌桶)→ Redis 预减库存(Lua 保证原子)→ 异步下单(MQ 削峰)→ DB 乐观锁扣减(`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`);
- 防超卖:库存判断与扣减必须原子;防刷:限购、风控。

### 11.4 订单 30 分钟未支付自动取消?
- **延迟队列**:Redis ZSet(score 为到期时间戳,定时轮询 `ZRANGEBYSCORE`)、RabbitMQ 死信队列、RocketMQ 延迟消息;
- 或定时任务扫表(数据量大时要分片 + 索引 `status + create_time`)。

### 11.5 权限模型(RBAC)怎么设计?
- 表:`sys_user`、`sys_role`、`sys_menu(permission)`、`sys_user_role`、`sys_role_menu`;
- 登录后查用户权限集合(可缓存在 Redis),前端动态生成路由与按钮显隐,**后端接口仍必须校验**(前端隐藏只是体验,不是安全边界)。

### 11.6 慢接口怎么排查?
先定位(`traceId` + 日志耗时打点/APM)→ 分类:
① SQL 慢(`EXPLAIN`、加索引、优化深分页);② 外部调用慢(加超时、熔断、并行化);③ 锁竞争(缩小事务、改用乐观锁);
④ GC 停顿(`jstat`)。

### A1. JWT 生成与解析(jjwt 0.12+ 新 API)
```java
private SecretKey key() {
    return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
}
public String createToken(Long userId, String username) {
    Date now = new Date();
    return Jwts.builder()
            .subject(String.valueOf(userId))
            .claim("username", username)
            .issuedAt(now)
            .expiration(new Date(now.getTime() + expireSeconds * 1000))
            .signWith(key())
            .compact();
}
public Claims parse(String token) {
    return Jwts.parser().verifyWith(key()).build()
            .parseSignedClaims(token).getPayload();
}
```
