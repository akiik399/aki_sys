# 用户注册 / 忘记密码 / 验证码登录 —— 设计方案

> 目标:给公开站点加一套**访客账号体系**,支持邮箱注册、邮箱验证码免密登录、忘记密码重置。
> 已确认的三个前提:① 注册对象是**站点访客**(公开注册) ② 验证码走**邮箱** ③ 站点用户放**独立的 `site_user` 表**,与 `sys_user` 彻底分开。

---

## 一、先说最要紧的:这个功能有一个越权陷阱,必须先堵上

这是整套方案里**唯一一个"做错了会出安全事故"的地方**,其他都只是工作量问题。

### 陷阱长什么样

现有 `AuthService.login()` 是这么签发 token 的:

```java
String token = jwtUtil.createToken(user.getId(), user.getUsername());   // sub = 用户ID
redisTemplate.opsForValue().set(RedisKeys.loginToken(token), String.valueOf(user.getId()), ...);
```

而 `AuthInterceptor` 校验通过后会执行:

```java
Long userId = jwtUtil.getUserId(claims);
UserContext.set(userId, claims.get("username", String.class));   // 之后 /api/** 全部信任它
```

**问题**:如果站点用户复用这套逻辑,那么一个注册访客的 token 里 `sub = 1`(他自己在 `site_user` 里的 id)。而 `sys_user` 里 **id=1 就是 admin**。同一串 JWT、同一个 Redis 键前缀、同一个 `UserContext`,拦截器无法分辨这是"站点访客 1 号"还是"管理员 1 号"——

> **结果是:任何注册用户只要拿到自己的 token,就能调 `/api/users`、`/api/roles` 等后台接口,身份被当成管理员。**

这不是"注意一下"能解决的,必须在设计层面隔离。

### 必须遵守的三条隔离规则

| 维度 | 规则 |
|---|---|
| **JWT** | 加 `scope` claim:`admin` / `site`。两个拦截器各自只接受自己的 scope,不匹配直接 401 |
| **Redis 键** | 登录态分前缀:`aki:login:admin:{token}` 与 `aki:login:site:{token}`,互不可见 |
| **接口前缀** | 后台 `/api/**`(现状不动);站点用户接口统一走 **`/api/account/**`**,只由 `SiteAuthInterceptor` 管 |
| **数据来源** | `UserContext` 区分类型(或站点侧另开 `SiteUserContext`),站点接口**永远不查 `sys_user` 表** |

这样即使将来有人在站点侧写出漏洞,他能拿到的也只是自己的访客身份,够不到后台。

## 二、数据模型

### 2.1 新表 `site_user`(站点访客)

```sql
CREATE TABLE IF NOT EXISTS `site_user` (
    `id`            BIGINT       NOT NULL AUTO_INCREMENT,
    `email`         VARCHAR(120) NOT NULL COMMENT '邮箱(登录名)',
    `password`      VARCHAR(100) DEFAULT NULL COMMENT 'BCrypt;纯验证码用户可为空',
    `nickname`      VARCHAR(50)  NOT NULL COMMENT '昵称',
    `avatar`        VARCHAR(500) DEFAULT NULL COMMENT '头像地址',
    `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
    `email_verified` TINYINT     NOT NULL DEFAULT 0 COMMENT '邮箱是否已验证',
    `last_login_at` DATETIME     DEFAULT NULL COMMENT '最近登录时间',
    `login_count`   INT          NOT NULL DEFAULT 0,
    `created_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_site_user_email` (`email`),
    KEY `idx_site_user_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='站点访客账号';
```

设计取舍:
- **只留 email,不做 username/phone**:邮箱既是登录名也是验证通道,少一个字段就少一处唯一性冲突和一套校验。将来要支持手机号,再加 `phone` 列并让 `email`/`phone` 至少一个非空即可。
- **`password` 允许为空**:验证码登录是免密的,有些人根本不会设密码。设为 `NULL` 表示"该账号只能用验证码登录"。
- **`email_verified` 单独一列**:虽然本方案里注册即验证(注册流程就要求填验证码),但保留这列,方便以后做"先注册后验证"或"改绑邮箱"。
- **落 `site_user_init.sql`,幂等**(全部 `CREATE TABLE IF NOT EXISTS`),沿用 `homepage_init.sql` 的写法。

### 2.2 验证码和一次性凭证:一律放 Redis,不进库

验证码是**短命数据**(5 分钟),进 MySQL 只会带来一堆过期清理逻辑和一次无谓的磁盘往返。Redis 天然带 TTL,而且现在就已经在用了。

### 2.3 Redis 键设计(全部带命名空间,便于排查和单独清理)

| 键 | 值 | TTL | 用途 |
|---|---|---|---|
| `aki:code:reg:{email}` | 6 位数字 | 5 min | 注册验证码 |
| `aki:code:reset:{email}` | 6 位数字 | 5 min | 重置密码验证码 |
| `aki:code:login:{email}` | 6 位数字 | 5 min | 登录验证码 |
| `aki:code:try:{scene}:{email}` | 尝试次数 | 5 min | 单个验证码最多校验 5 次,防暴力猜码 |
| `aki:code:cooldown:{scene}:{email}` | 1 | 60 s | 发送冷却,防连点 |
| `aki:code:quota:{email}:{yyyyMMdd}` | 当日发码数 | 至次日 | 每邮箱每日上限(建议 10 条) |
| `aki:rate:ip:{ip}:{yyyyMMddHHmm}` | 计数 | 1 min | 每 IP 每分钟发码上限(建议 5 条) |
| `aki:reset:{token}` | userId | 10 min | 验证码校验通过后换发的一次性重置令牌 |
| `aki:captcha:{id}` | 图形验证码答案 | 2 min | 图形验证码(见第五节) |
| `aki:login:site:{token}` | siteUserId | 8 h | 站点登录态(与 `aki:login:admin:` 并列) |
| `aki:login:site:user:{userId}` | token 集合(Set) | 8 h | 反向索引,用于"改密后踢下线" |

> ⚠️ **别用 `KEYS aki:*` 排查**,会阻塞 Redis。用 `SCAN`。键前缀分开的另一个好处就是可以按前缀批量清理。

## 三、接口设计

### 3.1 公开接口(不需要登录,走 `/api/public/**` 或新增豁免)

| 方法 | 路径 | 入参 | 说明 |
|---|---|---|---|
| GET | `/api/public/captcha` | — | 返回图形验证码图片 + `captchaId` |
| POST | `/api/public/email-code` | email, scene(reg/reset/login), captchaId, captchaCode | 发送邮箱验证码 |
| POST | `/api/public/register` | email, code, nickname, password | 注册并直接登录(返回 token) |
| POST | `/api/public/login-by-code` | email, code | 验证码免密登录 |
| POST | `/api/public/reset-password/verify` | email, code | 校验码 → 返回一次性 `resetToken` |
| POST | `/api/public/reset-password/confirm` | resetToken, newPassword | 用 resetToken 改密 |

**为什么重置密码拆成两步**:让"改密码"这个动作不需要再传一次验证码,避免用户在这一步等码/码过期;同时 `resetToken` 一次性、10 分钟,泄露窗口比验证码更短。

### 3.2 站点用户接口(需 `scope=site` 登录态)

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/account/logout` | 退出(删自己的 Redis 登录态) |
| GET | `/api/account/me` | 当前访客信息 |
| PUT | `/api/account/profile` | 改昵称/头像 |
| PUT | `/api/account/password` | 改密码(需旧密码),**改完踢掉自己所有会话** |
| PUT | `/api/account/email` | 改绑邮箱(需新旧邮箱各验一次码) |

### 3.3 后台管理站点用户(需 `scope=admin`)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/site-users` | 分页列表(沿用 MyBatis-Plus 分页) |
| PUT | `/api/site-users/{id}/status` | 启用/禁用 |

后台只需要这两个就够:访客账号不需要在后台做复杂编辑。

## 四、登录态与"改密踢下线"

站点侧复用现有 JWT + Redis 双校验的模式,但**键和 scope 分开**:

```
创建 token  ->  aki:login:site:{token} = userId          (TTL 8h)
             ->  SADD aki:login:site:user:{userId} {token}
校验        ->  scope 必须是 site,且 aki:login:site:{token} 存在
```

**改密/重置密码后必须让该用户所有 token 立即失效**,否则盗号者手里的 token 照样能用(这正是"改密码"这个动作的意义所在)。做法:

```
SMEMBERS aki:login:site:user:{userId}
  -> 逐个 DEL aki:login:site:{token}
  -> DEL aki:login:site:user:{userId}
```

> 替代方案是给用户表加 `token_epoch` 字段、JWT 里带上 epoch,校验时比对。好处是不用维护 Set,代价是每次请求多查一次库(或缓存)。本方案用户量小,反向索引更简单直接。

## 五、防刷:公开注册一定会被机器人盯上

个人站点的注册接口一旦上线,基本可以确定会收到垃圾注册和"邮件轰炸"利用。**发验证码的接口是全站最危险的接口**——它能让攻击者用你的域名给你的 SMTP 额度打满,或给第三方邮箱发骚扰信。

四道闸,从便宜到贵:

1. **图形验证码**(必须有)。发码接口强制带 `captchaId + captchaCode`,一次性消费(验完即删),2 分钟过期。
   - 自研极简版即可:服务端生成 4 位字符,用 Java2D 画一张带干扰线的 PNG,答案存 Redis。**不引第三方依赖**。
   - 若不想自研,可引 `com.github.penggle:kaptcha`。
2. **冷却 + 限额**(第二节的 Redis 键)。同一邮箱 60 秒内只能发一次,每日上限 10 次;同 IP 每分钟上限 5 次。
3. **邮箱验证闭环**。注册必须验码成功,不验码的账号不存在,垃圾注册就进不来。
4. **统一话术,防账号枚举**。以下场景一律返回同样的成功提示,不要区分"该邮箱已注册/未注册":
   - 注册:邮箱已存在 → 提示"验证码已发送"(其实不发,或发一封"你已注册"的提示信)
   - 忘记密码:邮箱不存在 → 同样提示"验证码已发送"
   - 如果不这样做,攻击者可以批量探测你的用户表里有哪些邮箱

另外建议**记录注册来源 IP 和时间**(以后要封禁有据可查),以及**可选的开关 `AKI_REGISTER_ENABLED`**:不想开放时一键关掉注册接口,不用改代码重新发包。

## 六、邮件通道

### 6.1 依赖与配置

需要新增一个依赖:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-mail</artifactId>
</dependency>
```

生产配置全部走环境变量(沿用现有 `AKI_*` 约定),补充到 `application-prod.yml`、`deploy/aki-admin.env.example`:

```
AKI_MAIL_HOST=smtp.qq.com
AKI_MAIL_PORT=465
AKI_MAIL_USERNAME=你的邮箱@qq.com
AKI_MAIL_PASSWORD=SMTP授权码       # 注意:不是邮箱登录密码
AKI_MAIL_FROM=你的邮箱@qq.com
AKI_MAIL_SSL=true
AKI_REGISTER_ENABLED=true
```

### 6.2 三个必须知道的部署坑

1. **云厂商普遍封禁出站 25 端口**(阿里云/腾讯云默认封,且基本不给解封)。所以**必须走 465(SSL)或 587(STARTTLS)**,不要用 25。
2. **QQ/163 邮箱要用"授权码"而不是登录密码**,在邮箱设置的"POP3/SMTP 服务"里开启并生成。
3. **发信要异步**,别让"发送邮件"阻塞 HTTP 响应(邮件服务器超时会让注册接口卡住)。用 `@Async` + 线程池,发信失败只记日志并返回"发送失败请重试",不要抛异常。

### 6.3 开发环境:别用真邮箱调试

本地起一个 **Mailpit**(或 MailHog)拦截所有外发邮件,Web 界面直接看验证码:

```
docker run -d -p 1025:1025 -p 8025:8025 axllent/mailpit
# application.yml(dev profile): host=127.0.0.1 port=1025,不需要账号密码
```

这样本地测试不用把验证码打进日志(打日志等于把验证码送给任何能看日志的人,生产环境尤其不能这么干)。

## 七、前端页面

### 7.1 路由规划(注意:**不要动现在的 `/login`**)

现有 `/login` 是**后台登录页**,已经被 `router/index.js` 的守卫和 README 记录了。站点访客的认证页放在公开区布局里,与后台完全分开:

| 路径 | 页面 | 归属 |
|---|---|---|
| `/login` | 后台登录(现状不动) | 管理区 |
| `/signup` | 注册(邮箱 + 验证码 + 昵称 + 密码) | 公开区 |
| `/signin` | 站点登录(两个 Tab:密码登录 / 验证码登录) | 公开区 |
| `/reset` | 忘记密码(三步:填邮箱 → 填码 → 设新密码) | 公开区 |

导航栏右上角:未登录显示「登录 / 注册」,已登录显示昵称 + 下拉(个人资料 / 退出)。

### 7.2 前端要点

- 验证码**倒计时按钮**(60 秒),与后端冷却对齐;倒计时期间禁用,防止用户连点触发风控
- 图形验证码**点击刷新**
- 邮箱格式、密码强度**前端先校验一遍**(后端必须再校验,不能只信前端)
- 站点 token 与后台 token **分开存** `localStorage`(`aki_site_token` vs 现有 `aki_token`),否则两边会互相覆盖登录态
- 新增 `src/api/account.js`,复用现有 `request.js`?**不能直接复用**——`request.js` 的响应拦截器在 401 时会清 `aki_token` 并跳 `/login`(后台登录页)。站点侧需要独立的 axios 实例或加一个开关参数,否则访客 token 失效会被错误地跳进后台登录页。

## 八、实施计划

分四步,**每步都能独立验收**:

| 阶段 | 内容 | 验收标准 | 估时 |
|---|---|---|---|
| **1 隔离改造(先做,最重要)** | JWT 加 `scope`;`RedisKeys` 拆前缀;新增 `SiteAuthInterceptor`;`/api/account/**` 放行规则 | 后台登录照旧可用;构造一个 `scope=site` 的 token 打 `/api/users` 必须 401 | 0.5 天 |

## 十、风险与注意点汇总

1. **越权(最高优先级)**:两条认证域必须靠 scope + 键前缀 + 接口前缀三重隔离,见第一节。
2. **邮件配额被打满**:发码接口必须有图形验证码 + 冷却 + 日限额,否则你的 SMTP 账号会被封。
3. **账号枚举**:注册/找回密码的返回值必须统一,不能泄露"该邮箱是否已注册"。
4. **改密后旧 token 必须失效**:否则盗号者仍能继续使用。
5. **验证码绝不能打进日志**:生产日志一旦泄露,等于把所有人的验证码公开。用 Mailpit 在开发期看,不要用日志代替。
6. **前端 axios 必须隔离**:现有 `request.js` 的 401 处理会跳 `/login`(后台),站点侧复用会导致访客被推进后台登录页。
7. **两个 token 的 localStorage 键必须不同**,否则互相覆盖。
8. **注册开关**:留 `AKI_REGISTER_ENABLED`,被刷爆时能一键关掉。
9. **别给站点用户任何后台角色**:`site_user` 表里**没有 role_id 字段**,这是刻意的——没有字段就不存在配错的可能。

## 十一、这套东西的面试价值(顺带)

这套功能正好是面试里区分"增删改查"和"做过认证体系"的分水岭,能讲的硬点:

- **越权隔离设计**:为什么两个用户表不能用同一套 token(可以完整复述第一节的推演,很能体现安全意识)
- **短信/邮件验证码的防刷四道闸**,以及"发码接口是全站最危险的接口"这个判断
- **改密踢下线**的两种实现(反向索引 vs token epoch)及取舍
- **防账号枚举**为什么重要、统一话术怎么设计
- 为什么验证码放 Redis 而不是 MySQL(短命数据 + TTL 原生支持)
